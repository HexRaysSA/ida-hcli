### 3. Python Dependencies (pip_packages / pythonDependencies) -- NOT Recursive for Components

**This is a critical finding: Python dependency installation is NOT recursive for components.**

The installation of Python dependencies happens in `_install_plugin_archive()` at `/Users/user/code/hex-rays/ida-hcli/src/hcli/lib/ida/plugin/install.py`, lines 772-793:

```python
python_dependencies = get_python_dependencies_from_plugin_archive(zip_data, metadata)
```

This call passes `metadata` -- which is the **root suite's metadata only**. The function `get_python_dependencies_from_plugin_archive()` (in `__init__.py`, line 744) reads `metadata.plugin.python_dependencies`, which is the root plugin's `pythonDependencies` field. It does NOT recursively collect `pythonDependencies` from component manifests.

There is no code anywhere that:
- Iterates over components to collect their `pythonDependencies`
- Calls `get_python_dependencies_from_plugin_archive()` or `get_python_dependencies_from_plugin_directory()` for each component

The same is true for `validate_can_install_python_dependencies()` (line 522) -- it validates only the root metadata's Python dependencies.

Similarly, `collect_plugin_dependencies()` (line 402) iterates over `get_installed_plugin_records()`, which only returns top-level plugins. Components are subdirectories within a suite and are not enumerated by `get_installed_plugin_records()`, so their Python dependencies are never collected for the global dependency set.

**Conclusion: If a component declares its own `pythonDependencies`, they will be silently ignored during installation.** The suite root must declare all needed Python dependencies in its own `pythonDependencies` field.

**Settings storage:** `/Users/user/code/hex-rays/ida-hcli/src/hcli/lib/ida/plugin/settings.py`

Settings are stored in `ida-config.json` keyed by plugin name. The settings system uses `find_installed_plugin()` (line 27) which calls `get_installed_plugin_records()` -- this only returns top-level plugins, not components.

However, components have their own `ida-plugin.json` files which can declare settings. At runtime, a component plugin can call `get_current_plugin()` (line 166) which walks the call stack to find the plugin directory. Since the component's code lives under `$IDAUSR/plugins/&lt;suite-name&gt;/&lt;component-name&gt;/`, and the function matches against `$IDAUSR/plugins/`, it would find the suite directory name, not the component directory name. Specifically, the code at line 208 extracts `module_relative_path.parts[0]` which would be the suite name. So at runtime, `get_current_plugin()` from a component's code would return the suite name, not the component name.

**Conclusion: Component settings are not handled during installation. If a component declares settings, they are not prompted for or configured.** Settings configuration is only done for the root suite plugin.

### Key Architectural Observations

2. **Components are hidden from top-level enumeration**: `get_installed_plugin_records()` does not recurse into suite subdirectories.

3. **Neither `pythonDependencies` nor `settings` are processed recursively for components**: only the root suite's values are used during installation. This means the suite root must aggregate all Python dependencies from its components.

4. **Components can nest up to 10 levels deep** (controlled by `MAX_COMPONENT_DEPTH` in components.py line 19).
