## Review Findings for PR #330

### 1. BUG: `verify_env_var_in_subprocess` POSIX path is a no-op
**File:** `platform_env.py:528-536`
**Severity:** Bug

The POSIX branch passes `env={**os.environ, name: expected}` to the subprocess, then checks if the subprocess echoes that value back. Since `execute_configuration_plan` already set `os.environ[name] = value` (line 505), the check always succeeds trivially. It does not verify persistence — it verifies that subprocess.run passes env correctly.

The Windows branch actually reads from the registry (`"User"` scope), so it tests real persistence.

**Suggested fix:** Remove the `env=` override. Since `execute_configuration_plan` already sets `os.environ`, the subprocess will inherit it anyway. But the docstring already says "This only confirms the current process environment; it does not confirm persistence across login sessions" — so this is working as documented, it's just that the explicit `env=` override is misleading dead code that obscures what's actually being tested. Remove the `env=` parameter to make it obvious the check is validating `os.environ` propagation (set at line 505).

### 2. BUG: `execute_configuration_plan` sets `os.environ` unconditionally
**File:** `platform_env.py:505`
**Severity:** Bug

`os.environ[plan.env_var_name] = plan.env_var_value` runs even when all steps failed. The caller (`configure_env_var` at line 135) checks `any_failed` and returns `False, None` — but the process env var is already mutated. On Windows where the single step is the PowerShell command, if it fails, the process env is set but nothing was persisted. Not harmful in practice (the process is about to exit), but inconsistent with the "False" return.

**Suggested fix:** Only set `os.environ` when at least one step succeeded, or move the `os.environ` set into the caller after checking results.
